# Лаборатори 3 Чанарын сценарио SLO ба k6 threshold

Оюутны нэр: Н. Төгөлдөр
Оюутны код: B232270009
Огноо: 2026-11-18

Локал Express API дээр чанарын сценарио бичиж, хэмжүүрүүдийг SLO болон k6 threshold болгон шалгав. Хэвийн тест PASS, crash оруулсан тест availability болон reliability дээр FAIL, зориуд чангалсан report threshold FAIL болсон.

## Орчин

`k6 version` командын гаралт ([эх файл](results/version.txt)):

```text
k6.exe v2.4.0 (commit/dd9395906d, go1.26.11, windows/amd64)
```

Windows PowerShell, Node.js v26.13.0, Express; API зөвхөн http://127.0.0.1:3000 дээр ажиллана. Node dependency хувилбарууд package-lock.json-д хадгалагдсан.

## Сценарио ба SLO

Нэг давталт `/cart/add`, `/report`, `/pay` руу дараалан хүсэлт илгээгээд 1 секунд хүлээнэ. 20 VU нь хаалттай ачааллын загвар; хэвийн үед ойролцоогоор 46 хүсэлт/сек, endpoint бүрд 15 хүсэлт/сек төлөвлөв. Энэ нь тогтмол arrival rate биш.

| Хэсэг | Performance | Reliability | Availability | Report performance |
| --- | --- | --- | --- | --- |
| Тойм | Сагсанд бараа хурдан нэмэх | Төлбөрийн алдааг хязгаарлах | Crash дараа үйлчилгээг сэргээх | Тайланг хугацаанд нь авах |
| Системийн төлөв | API ажиллаж байгаа | API ажиллаж байгаа, pay 5% алдаатай | Эхлээд ажиллана, дараа зогсоод асна | API ажиллаж байгаа |
| Орчны төлөв | Локал, 20 VU, 1 минут | Локал, 20 VU, 1 минут | Локал, 20 VU, 2 минут | Локал, 20 VU, 1 минут |
| Гадаад өдөөлт | Хэрэглэгч POST /cart/add хийх | Хэрэглэгч POST /pay хийх | Тест эхэлснээс 30 секундэд серверийг унагаж, 10 секундийн дараа асаах | Хэрэглэгч GET /report хийх |
| Шаардлагатай хариу | HTTP 200, бараа нэмэгдэнэ | HTTP 200, төлбөр батлагдана | Асаасны дараа хүсэлтүүд дахин HTTP 200 авна | HTTP 200, rows 20000 |
| Хэмжүүр | cart latency p95 <20 мс | pay error rate <8% | Бүх хүсэлтийн амжилт ≥90%; VU бүрийн сэргэлт ажиглах хугацааны p95 <12 секунд | report latency p95 <450 мс |

Reliability, availability нь хувь хэмжүүр тул p95 болгон хувиргаагүй. Availability-ийн сэргэлтийн хугацаанд p95 ашиглав. Сценарионууд нь локал бодит үйлдэлтэй, хэрэглэгчид үнэ цэнэтэй, endpoint ба өдөөлт нь тодорхой, ачаалал ба цонх нь нарийн, үр дүнг HTTP статус болон хэмжигдэх хугацаагаар ойлгомжтой шалгана.

| Сценарио | SLI | Босго | Цонх ба нөхцөл | k6 threshold |
| --- | --- | --- | --- | --- |
| Performance | cart latency | p95 <20 мс | 20 VU, 1 минут | http_req_duration{name:cart}: p(95)<20 |
| Reliability | pay error rate | <8% | 20 VU, 1 минут | http_req_failed{name:pay}: rate<0.08 |
| Availability | HTTP 200 хүсэлтийн хувь | ≥90% | 20 VU, 2 минут, 10 секундийн crash | checks: rate>=0.90 |
| Recovery | VU бүрийн анхны холболтын алдаанаас дараагийн амжилттай cart хүсэлт хүртэл | p95 <12000 мс | Chaos үед 20 VU тус бүр нэг ажиглалт | outage_recovery_ms: p(95)<12000; recovery_samples: count>=20 |
| Report | report latency | p95 <450 мс | 20 VU, 1 минут | http_req_duration{name:report}: p(95)<450 |

Cart нь I/O хүлээлтгүй тул 200 мс-ээс хатуу 20 мс босго сонгов. Pay-д зориудын 5% алдаа байгаа тул түүврийн хэлбэлзэлд зай үлдээж 8% сонгов. Report-ийн 200–400 мс хүлээлтэд scheduler болон HTTP overhead-д 50 мс зай үлдээв. Сэргэлтийн 12 секунд нь 10 секундийн зогсолт, процесс асах болон дараагийн probe хүртэлх хугацааг хамарна. 2 минутын availability 90% байвал цагаар тооцсон error budget = 120 × (1 − 0.90) = 12 секунд. Хүсэлтээр тооцсон budget = нийт хүсэлт × 0.10; энэ нь 12 секундтэй шууд адил биш.


## Ажиллуулах

Төслийн үндсэн хавтаснаас:

```powershell
cd .\Lab3
npm.cmd ci
npm.cmd run check
npm.cmd run experiments
```

Runner нь portable k6-г ../.tools/k6/k6-v2.4.0-windows-amd64/k6.exe замаас ашиглана. Тусдаа суулгасан k6 ашиглах бол run-experiments.cjs-ийн k6 замыг тохируулна. Туршилтууд 1 минут, 2 минут, 1 минут гэсэн дарааллаар ажиллана. Runner өөрөө асаасан API процессоо chaos тестийн 30 дахь секундэд зогсоож, 10 секунд хүлээгээд дахин асаана. Энэ нь Ctrl+C ба гараар дахин асаах үйлдлийг давтагдах байдлаар автоматжуулсан. Бүх тестийн дараа API-г зогсооно. 3000 порт өмнө нь ашиглагдаж байвал runner туршилт эхлүүлэхгүй.

Тус тусад нь ажиллуулах бол API-г эхний терминалд `node server.js` гэж асаагаад хоёр дахь терминалд:

```powershell
$k6Exe = (Get-ChildItem ..\.tools\k6 -Filter k6.exe -Recurse).FullName
& $k6Exe run --quiet --no-color --summary-mode full slo-test.js
$LASTEXITCODE
& $k6Exe run --quiet --no-color --summary-mode full -e CHAOS=1 slo-test.js
$LASTEXITCODE
& $k6Exe run --quiet --no-color --summary-mode full slo-test-fail.js
$LASTEXITCODE
```

Гараар chaos ажиллуулах үед нөгөө терминалд API-г 30 дахь секундэд зогсоож, 10 секундийн дараа дахин асаана. `CHAOS=1` нь цонхыг 2 минут болгож, recovery хэмжүүрийг идэвхжүүлдэг; серверийг зогсоох үйлдлийг зөвхөн runner автоматжуулдаг.

## Chaos ба error budget

Бодит availability = 4944 / 5667 × 100 = 87.24%. 90%-ийн SLO-д нийт 5667 хүсэлтээс хамгийн ихдээ 566 хүсэлт унах боломжтой. Бодитоор 723 хүсэлт унасан тул budget-ийг 157 хүсэлтээр хэтрүүлсэн. Иймээс availability threshold FAIL болсон. Pay error rate 15.93% болж 8%-ийн босгыг мөн давсан: сервер унтарсан үед төлбөрийн бүх хүсэлт алдана.

Цагаар тооцсон budget 12 секунд бөгөөд зориудын зогсолт 10 секунд байсан. Гэвч сервер зогсоход report-ийн 200–400 мс хүлээлт байхгүй болж, connection refused хурдан буцдаг тул давталтын хугацаа богиносож, уналтын үеийн нэг секундэд илүү олон хүсэлт илгээгддэг. Үүн дээр pay-ийн хэвийн үеийн зориудын алдаа нэмэгдэнэ. Тиймээс цагаар budget-д багтсан ч хүсэлтийн budget хэтэрч болно. Энэ хэмжилтийн нөхцөлд 10 секундийн crash, pay-ийн алдааг хамтад нь тооцсон 90%-ийн хүсэлтийн SLO хангагдаагүй; хэмжилтийн дараа босгыг сулруулаагүй.

VU бүрийн анхны cart холболтын алдаанаас дараагийн амжилттай cart хүсэлт хүртэлх сэргэлтийн p95 11126.10 мс, ажиглалт 20 байв. Энэ нь 12000 мс-ийн босгыг хангасан. Controller-ийн stop болон ready цаг, recovery_ms нь chaos.txt дотор бий. VU хэмжилт нь probe-ийн 1 секундийн хүлээлт болон report-ийн хариуны хугацаанаас хамаардаг; яг процессын downtime биш. Эдгээр 20 хэмжилт нь нэг crash-ийн давхцсан ажиглалт тул олон тусдаа эвдрэлийн урт хугацааны p95 гэж үзэхгүй.

Availability-г cart эсвэл health probe-ийн хугацааны түүврээр, reliability-г сервер хүрэх боломжтой үеийн pay HTTP 500 / хүрсэн pay хүсэлтээр тусгаарлан хэмжиж болно. Энэ лабораторийн өгсөн SLI-г хэвээр үлдээсэн тул одоогийн pay error rate-д сүлжээний алдаа давхар багтсан.

## Зориудын FAIL

slo-test-fail.js нь бусад босгыг хадгалж, report-ийн p95 босгыг 450 мс-ээс 100 мс болгосон. Хэмжсэн report p95 398.45 мс тул p(95)<100 нөхцөл зөрчигдсөн. [fail.txt](results/fail.txt)-ийн THRESHOLDS хэсгийн report мөр, төгсгөлийн threshold зөрчсөн лог, exit=99 нь нотолгоо болно. Cart-ийн босгыг 50 мс болгоход localhost дээр хурдан хэвээр учраас найдвартай FAIL үүсгэхгүй. CI нь k6 процессын 99 exit code-оор шалгалтыг амжилтгүй болгох боломжтой.

## Дүгнэлт

Сценариогоос SLO гаргахад хамгийн хэцүү нь хэмжих нэгж, ачаалал, хугацааны цонхоо нэг утгатай тодорхойлох байв. Cart-ийн 20 мс босго нь хэвийн тестийн 3.62 мс p95-тай харьцуулахад бодитой нөөцтэй байсан. Pay-ийн зориудын алдааг харгалзсан 8%-ийн босгыг хэвийн тест хангасан. Report-ийн 450 мс босго хэвийн үед хангагдсан боловч 100 мс болгож чангалмагц тест FAIL болсон. Энэ үед HTTP хүсэлт амжилттай байсан ч хугацааны шаардлага зөрчигдөж болдгийг харлаа. Chaos туршилтад 10 секундийн зогсолт цагаар тооцсон 12 секундийн budget-д багтсан ч хүсэлтийн availability шаардлага хангагдаагүй. Сервер унахад давталт хурдан дуусдаг учраас хугацааны хувь ба хүсэлтийн хувийг адилтгаж болохгүйг энэ туршилт харуулсан. Нэг crash availability болон reliability хоёр SLO-г зэрэг зөрчсөн тул SLI-үүдийн хамрах хүрээг тусгаарлан тодорхойлох хэрэгтэй. Сэргэлтийн p95 босго хангагдсан ч нэг crash-ийн ажиглалтаар урт хугацааны найдвартай ажиллагааг батлах боломжгүй.
